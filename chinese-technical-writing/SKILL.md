# 中文技术写作

把已确认的技术事实写成读者能够准确执行、验证和维护的中文。表达优化不能改变事实、业务语义或权威来源的含义。

## 工作流程

### 1. 确定任务与交付形式

识别任务类型：

- 起草：根据事实、提纲或来源形成新文档。
- 审查：发现问题，不改写全文。
- 重写：保留原始语义并改进表达。
- 审查并重写：说明关键问题后提供修订稿。

确认读者、用途、任务范围和用户要求的交付形式。不要把审查过程、问题清单或补充章节加入用户只要求的最终稿。

### 2. 确认权威来源

确认本次任务以哪些材料为准，例如接口契约、需求、源码、术语表、现有文档或用户说明。源码可能描述当前实现，需求可能描述目标行为，不能预设固定的来源优先级。

多个权威来源冲突时，明确指出冲突。不要静默选用其中一个版本。

### 3. 建立事实基线

重写前，在内部提取原子事实。每个事实至少检查：

- 主体、动作和对象。
- 条件、顺序和可观察结果。
- 否定、范围、数量、单位、状态和例外。
- “必须、应、宜、可、不得、仅、至少、最多、默认、除非”等规范性语气。

除非权威来源明确否定、替代或废止某个事实，否则修订稿必须保留该事实及其强度。不要因为另一条事实更具体，就删除原事实中不同的动作或职责。

### 4. 建立术语基线

一个已确认概念使用一个首选术语。

- 保留代码标识符、接口字段、产品名和用户指定名称。只有用户明确要求变更，且权威来源提供精确替换值时，才修改这些名称。
- 名称相近不表示概念相同。只有权威来源明确给出别名、重命名或同一性关系时，才能合并名称。
- 区分相近但不同的概念。不要因为统一术语而合并业务边界。
- 首次出现不常见缩写时写出全称，但项目已定义的缩写和精确标识符除外。
- 无法确认两个名称的映射关系时，将其作为术语映射问题处理。

### 5. 判断歧义是否阻塞

把信息缺口分为两类：

- 阻塞性歧义：不同答案会改变当前文档中的事实、接口契约、业务规则、职责边界、术语映射或规范性语气。提出具体问题后暂停，不输出看似完整的修订稿。
- 非阻塞性缺口：未知信息不影响当前范围内的安全起草或重写。不要补全未知事实；仅在它影响文档使用时列为待确认项。

文档类型检查项是审查维度，不是强制补全清单。不要因为完整文档通常需要某项信息，就扩大局部润色或重写的范围。

### 6. 使用受控表达

1. 一个句子表达一个主要动作。存在必要的顺序、条件或因果关系时，可以保留从句。
2. 优先使用明确的主体、动作和对象。执行者无关或确实未知时，可以使用被动表达。
3. 使用具体动词，例如“创建”“查询”“验证”“返回”。不要用“进行处理”“实现能力”等空泛表达代替已知动作。
4. 发现“快速”“高效”“适当”等不可验证声明时，先判断它是否承载业务承诺。只有确认不影响语义时才能删除；否则询问其判断标准。
5. 删除不增加信息的修饰语，但不得删除事实、约束、条件或承诺。
6. 条件写在对应动作之前。操作步骤按实际执行顺序排列。
7. 指代必须唯一。指代可能对应多个对象时，重复具体名称。
8. 保留必要的领域术语。不要为了使用日常词而改变专业含义。
9. 不设置机械字数上限。只在句子包含多个独立事实或难以一次理解时拆分。

## 不可破坏的约束

起草、审查或重写时，不得：

1. 在来源没有明确映射时，把两个名称判定为同一概念、别名或同一组件。
2. 为了简洁而删除未被权威来源否定的事实、动作、职责或约束。
3. 增强、削弱或删除规范性语气、否定、范围、条件、顺序、数量、状态或例外。
4. 根据行业惯例推断状态码、默认值、数据所有权、依赖方向、调用关系、幂等性或性能指标。
5. 把文档类型检查项当成强制补全项，扩展用户当前要求的范围。
6. 在用户没有明确要求变更，或权威来源没有提供精确替换值时，修改代码标识符、字段名、命令、路径、链接目标、锚点、占位符或精确错误文本。
7. 把语言更清晰当成事实已经正确的证据。
8. 在阻塞性歧义尚未确认时输出可直接发布的修订稿。

## 按文档类型检查

只检查当前任务范围内适用的项目。

### README 和操作指南

检查目标读者、用途、前置条件、最短可执行路径和验证结果。未确认变更时，不要改写命令、路径或环境要求；确认变更时，使用权威来源提供的精确值。

### API 文档

检查用途、方法与路径、认证、输入、成功响应、错误条件和副作用。局部任务不要求补齐全部契约。不要根据惯例发明状态码、默认值或幂等语义。

### 架构文档

检查组件身份、职责与非职责、依赖方向、数据所有权和关键调用路径。不要从名称相似推断组件相同。

### ADR

区分背景事实、已作决定、备选方案、选择理由、后果和状态。不要把计划、决定和当前实现混为一谈。

### 操作步骤

检查前置条件、动作顺序和预期结果。未确认变更时，原样保留命令、路径、按钮、参数以及安全警告中的关键字面值；确认变更时，使用权威来源提供的精确值。

### Agent 指令

只审查中文表达、术语和语义保真。Agent 行为、触发机制和指令结构由相应的 Agent 指令 Skill 决定。

## 输出规则

用户要求优先于默认格式。

### 审查

只输出问题。先列事实、契约和语义风险，再列清晰度与一致性问题。每项说明位置、影响和修改方向。

### 重写、润色或最终稿

只输出完整修订稿。不要附问题清单、写作过程或额外说明。

### 审查并重写

先列影响事实、契约或理解的关键问题，再输出完整修订稿。只有比较多项对应关系确实更清晰时才使用表格。

### 起草

直接输出完整文档。只有用户要求解释设计时，才补充写作决策。

存在非阻塞性缺口时，可在最终稿前列出必要的待确认项。没有必要的待确认项时省略该章节。

## 最终检查

交付前确认：

- 每个未被否定或替代的原子事实是否仍然存在？
- 是否擅自合并了名称相近但身份未确认的概念？
- 规范性语气、否定、条件、范围、顺序和例外是否保持不变？
- 是否增加了来源不支持的事实、关系、数值、状态或承诺？
- 输出内容和格式是否符合用户明确要求？
- 精确字面值和 Markdown 结构是否保持有效？

需要了解本 Skill 的依据和适用边界时，读取 [references/foundations.md](references/foundations.md)。
