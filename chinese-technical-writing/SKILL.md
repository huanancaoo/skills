# 中文技术写作

把技术事实写成读者能够准确执行、验证和维护的中文。清晰度高于文采；事实和既有术语高于措辞变化。

## 工作流程

### 1. 确定任务

识别任务属于以下哪一类：

- 起草：用户提供事实或提纲，需要形成新文档。
- 审查：用户需要发现问题，不要求改写全文。
- 重写：用户提供原文，需要保留语义并提高质量。

识别文档的读者、用途、事实来源和不可改变的术语。优先采用仓库源码、接口契约、现有术语表和用户明确说明。

如果缺失信息会改变业务语义、接口契约或职责边界，先提出具体问题。不要自行补全这些信息。

### 2. 建立术语基线

提取关键概念及其名称。对每个概念只使用一个首选术语。

- 保留代码标识符、接口字段、产品名和用户指定名称。
- 区分相近但不同的概念。例如，“用户”“客户”“会员”只有在定义相同时才能合并。
- 首次出现不常见缩写时，写出全称。通用缩写或项目已定义的缩写除外。
- 发现同义词混用时，说明冲突及建议采用的术语。

### 3. 检查事实与逻辑

逐项检查：

- 主体：谁执行动作？
- 动作：具体执行什么？
- 对象：动作影响什么？
- 条件：动作在什么条件下发生？
- 结果：系统产生什么可观察结果？
- 边界：职责包含什么，不包含什么？
- 验证：读者如何判断描述成立？

不要用语言优化掩盖事实缺口。无法从来源确认的内容应列为待确认项。

### 4. 使用受控表达

遵守以下规则：

1. 一个概念使用一个名称。同义词替换不能以牺牲一致性为代价。
2. 一个句子表达一个主要动作。存在顺序、条件或因果关系时，可保留必要的从句。
3. 优先使用“主体 + 动作 + 对象”。当执行者无关或确实未知时，可以使用被动表达。
4. 使用具体动词，例如“创建”“查询”“验证”“返回”。把“进行处理”“实现能力”等空泛表达改成真实动作。
5. 把“快速”“适当”“尽快”“一般”等不可验证表述改成明确条件或指标。来源没有指标时，不得编造数值。
6. 删除不增加信息的“相关”“方面”“赋能”“无缝”“高效”等词。
7. 条件写在动作之前。步骤按实际执行顺序排列。
8. 指代必须唯一。“该服务”“其”“它”可能指向多个对象时，重复具体名称。
9. 保留必要的领域术语。不要为了“简单”而改错专业含义。
10. 不强制机械字数上限。句子只在包含多个独立事实或难以一次理解时拆分。

### 5. 按文档类型检查

#### API 文档

说明接口用途、请求方法与路径、认证要求、输入、成功响应、错误条件和副作用。字段描述应包含类型之外的业务含义与约束。不要根据惯例发明状态码、默认值或幂等语义。

#### 架构文档

说明组件职责、非职责、依赖方向、数据所有权和关键调用路径。用可观察行为代替“能力建设”“统一赋能”等口号。

#### 操作步骤

一个步骤只包含一个主要操作。先写前置条件，再写动作和预期结果。命令、路径、按钮和参数必须与来源一致。

#### Agent 指令

写清触发条件、允许的动作、禁止的动作、决策边界和完成标准。避免互相冲突或无法验证的绝对要求。

## 输出格式

### 审查

按严重程度列出问题。每项包含：

- 原文位置或原句
- 问题类型
- 为什么会误解或无法验证
- 建议修改

只审查时，不附完整修订稿。

### 重写

使用以下结构：

```markdown
## 问题清单

| 位置 | 问题 | 影响 | 修改原则 |
|---|---|---|---|

## 待确认项

- 仅列出不能从来源确定、且会影响语义的事项。

## 修订稿

[完整、可直接使用的文档]
```

没有待确认项时省略该章节。修订稿不得悄悄改变原文的业务规则。

### 起草

直接输出完整文档。仅在用户要求解释设计时，补充“写作决策”。不要虚构原本不存在的问题清单。

## 最终检查

交付前确认：

- 同一概念是否只有一个名称？
- 每个关键动作是否有明确主体、对象和条件？
- 是否存在未经来源支持的数值、状态或承诺？
- API、架构或步骤是否形成完整链路？
- 修订是否保持原始业务语义？
- 标题、列表、代码和术语格式是否一致？

需要了解本 Skill 的依据和适用边界时，读取 [references/foundations.md](references/foundations.md)。
