# 分页、刷新与缓存

仅在任务需要对应能力时读取；这些规则保证数据一致性，不定义产品分页或离线策略。

## 分页契约

实现前明确页码或 cursor、首批请求、页大小、排序、筛选、结束标志、稳定标识及重叠数据是否可能出现。不能用“返回数量小于页大小”推断结束，除非接口明确保证；不能自行按某个字段去重。

分页状态只包含实际需要的内容：当前列表、下一页位置、是否结束、加载下一页与相应错误。初始请求的加载和错误继续由 `AsyncValue` 表达。

- 同一列表查询同一时刻只接受一个追加请求；只有成功提交该页后才推进页码或 cursor。
- 加载下一页失败不推进位置、不清空成功列表，也不触发自动重试。用户能否再次触发加载与错误展示方式由已确认交互决定。
- 刷新成功用首批结果替换当前列表与分页位置；不是把首批追加到旧列表。
- 更改筛选或开始刷新时生成新一轮请求标识；追加请求记录启动时的轮次和查询条件。结果提交前比较标识，旧轮次的成功、失败以及 `finally` 都不能改写新轮次状态。
- 按所有权取消旧的 Dio 请求以释放资源，并用轮次判定阻止已经完成或未能取消的旧结果提交。取消当前 feature 的请求不能取消其他消费者共享的请求。
- provider 销毁后不写状态。通过其生命周期关闭本轮资源；不要把轮次计数器做成跨页面全局变量。

加载时是否保留当前列表、刷新失败后是否继续显示旧内容、连续刷新是替换还是禁止，都属于交互契约；定义缺失时先澄清，不能借竞态保护改变用户操作语义。

## Repository 缓存

缓存必须有已确认的缓存对象、介质、容量或清理规则、有效期限及失效事件。没有这些定义时完成无缓存的数据链路，并说明缓存定义待确认；不能自行设定五分钟期限或长期有效。

- 由 Repository 唯一管理缓存读取、写入与失效。UI、Notifier 和 Dio interceptor 不各自创建一份业务缓存。
- key 包含影响结果的环境与查询条件；不同筛选、排序、分页位置的结果不能错误复用。
- 同一轮次检查也保护缓存写入：过期请求不能在状态提交被拒绝后继续把旧结果写进当前缓存。
- 只有契约明确允许的成功结果可以写入。空列表是有效数据还是异常、写操作影响哪些缓存，都按接口与业务定义处理。
- 到期判断使用可注入的时间来源，测试期限边界；失效依据是已定义的数据更新事件或主动清理动作。
- 不在网络错误时擅自回读旧缓存，不添加 stale-while-revalidate、离线同步或后台刷新。

## 时序验证

用可控 Future 完成顺序验证：旧查询晚于新查询完成、旧追加晚于刷新完成、旧失败与旧 `finally` 晚到、同页重复触发、追加失败后再次请求位置、provider 销毁、缓存到期和明确失效事件。检查最终列表、分页位置、加载标志、错误与缓存均属于当前轮次。

官方 API 查证：[Dio CancelToken](https://pub.dev/documentation/dio/latest/dio/CancelToken-class.html)、[Riverpod 生命周期](https://riverpod.dev/docs/concepts2/refs)。
